# M13.6 Agent-first Web 增强方案

## 1. 定位

EviMesh 的主要写入通道是 CLI、MCP、SDK 和用户自己的 Agent。Web 的主要职责是感知、阅读、解释、追溯和分享，不与 Agent 争夺复杂科研输入工作。

Design Read：面向科研人员的可信研究状态阅读器，采用高信息密度、低装饰、低运动的研究工具语言。

- `DESIGN_VARIANCE: 4`
- `MOTION_INTENSITY: 2`
- `VISUAL_DENSITY: 7`

## 2. 对外部构想的协议校正

### 2.1 不是简单的 Question、Claim、Evidence 树

EviMesh 的实际结构是多层有向图：

1. Project 容纳一个或多个 Question；
2. Question 通过 ResearchContract 定义边界，并拆解为 Task；
3. Attempt 承载参与过程，可产生 Claim、Run、Artifact 和 Evidence；
4. Claim 使用不可变 revision，并通过恰好 14 种 Claim→Claim 关系形成 DAG：`depends_on`、`supports`、`refutes`、`qualifies`、`reproduces`、`extends`、`supersedes`、`contradicts`、`derived_from`、`uses_method`、`uses_dataset`、`implements`、`verifies`、`challenges`；
5. Evidence 通过 `supports`、`refutes`、`qualifies`、`reproduces` 绑定具体 Claim revision；
6. VerificationReceipt 在指定 VerificationContract 与 Policy 下记录 outcome、独立性和 Finding；
7. Challenge 可触发 contested、refuted、retracted 或 dependency_tainted 等状态变化；
8. Frontier snapshot 表示某一时刻可供下游使用的 Claim revision 集合。

Web 必须允许用户在 Argument、Evidence、Verification 和 Frontier 四种视角之间切换，不能把所有关系伪装成父子树。

### 2.2 不使用虚构的支持度分数

当前协议没有通用的标量支持度，也不采用多数投票。界面不得把 Evidence 数量直接换算成百分比或进度条。

每个 Claim 使用可追溯的状态摘要：

- 当前 Claim state；
- 是否属于最新 Frontier；
- Evidence 按 supports、refutes、qualifies、reproduces 分组的数量与最近变化；
- Verification outcome 分布；
- implementation 与 data independence 分布；
- 未解决 Finding 的最高 severity；
- 活跃 Challenge 及影响范围；
- 最近一次 ResearchEvent；
- 所有结论对应的 Policy、Contract 和 revision。

任何未来派生评估都必须显示算法名称、Policy revision、输入集合和计算时间，不得只显示一个无法解释的颜色条。

### 2.3 不隐藏科研语义，只隐藏实现噪声

界面主文案使用“问题”“论点”“证据”“验证”“质疑”“当前前沿”等自然语言。稳定 ID、revision、hash、Policy 和签名仍可在“技术详情”中查看和复制，因为它们是可追溯科研记录的一部分。

数据库表名、repository、堆栈、内部路由和原始异常不得暴露。

## 3. Web 核心体验

### 3.1 首页是关注变化，不是全站内容流

登录后的首页优先显示用户关注的 Project、Question 和 Claim 的状态变化：

- 新增支持、反驳、限定或复现 Evidence；
- Verification outcome 或 independence profile 变化；
- 新 Finding 或 Finding severity 变化；
- 新 Challenge 及其影响；
- Claim state 变化；
- Frontier 新增、移除或替换 Claim revision。

变化等级只表达需要注意的程度，不表达真伪：

- critical：Frontier 污染、Claim refuted/retracted、critical Finding；
- attention：contested、major Finding、新反驳 Evidence；
- update：新支持、限定、复现、revision 或普通事件；
- quiet：关注对象在选定窗口内无变化。

每条变化必须回答“发生了什么”“为什么重要”“依据在哪里”，并链接到准确 revision 或 event。

### 3.2 论证浏览采用渐进展开

Question 页面默认展示：

1. 问题范围和 ResearchContract 摘要；
2. 最新 Frontier 中的 Claim；
3. contested、refuted 或最近变化的高关注 Claim；
4. 未解决 Task 和当前验证阻塞项。

Claim 默认只展示 statement、state、Frontier 状态和状态摘要。展开后依次显示关联 Claim、Evidence、Verification、Finding、Challenge 和 revision history。

图形视图必须提供等价的键盘可操作列表视图。颜色不得成为唯一信息载体。

### 3.3 Web 操作转为 Agent handoff

“补充证据”“提出质疑”“开始验证”“继续研究”等按钮默认打开 handoff sheet，而不是复杂表单。

handoff 内容包括：

- 用户意图；
- 对象稳定 ID 与 revision；
- 当前页面永久链接；
- 建议的 CLI 命令；
- 建议的 MCP resource 和 tool；
- 自然语言任务说明；
- 所需 token scope；
- 返回 Web 的 continuation URL。

handoff 不包含 API token、Cookie、私有数据正文或其他凭据。CLI 从本地配置读取认证，MCP 客户端使用自己的安全上下文。

浏览器无法可靠直接启动任意 MCP 客户端，因此第一版提供：

1. 复制自然语言任务；
2. 复制 CLI 命令；
3. 下载或复制结构化 handoff JSON；
4. 在支持的客户端中通过显式 adapter 打开。

现有 Web 表单保留在“手动提交”入口，作为无障碍、无 Agent 和故障回退路径，不再成为页面主动作。

### 3.4 分享使用不可变上下文

Project、Question、Task、Claim revision、Evidence、VerificationReceipt、Finding、Challenge、Frontier snapshot 和 ResearchEvent 都应具有可复制永久链接。

分享链接必须：

- 默认指向准确 revision 或 snapshot；
- 明确提示是否存在更新版本；
- 保留当前视角、选中对象和展开上下文；
- 为公开对象生成可读 Open Graph 摘要；
- 不在 URL 中放置认证信息或敏感 payload。

## 4. 明确非目标

- 不开发平台自有通用聊天 Agent；
- 不用 Evidence 数量生成真理分数；
- 不删除 CLI/MCP/SDK 能力；
- 不删除所有 Web 写入回退路径；
- 不改变现有稳定 ID、revision 或签名语义；
- 不把 Claim DAG 强制改成单父节点树；
- 不在 M13.6 引入社交点赞、排行榜或内容推荐算法。

## 5. M13.7 准入门槛

M13.6 完成后，进入成熟产品壳与身份接入重构前，目标用户必须能够：

1. 在 60 秒内说明一个 Question 当前处于什么阶段；
2. 区分支持、反驳、限定和复现 Evidence；
3. 找到影响 Claim 可接受性的 Verification、Finding 和 Challenge；
4. 判断 Claim 是否进入最新 Frontier，并追溯对应 revision；
5. 从 Web 生成 handoff，并通过 CLI 或 MCP 继续任务；
6. 分享一个不可变链接，让未登录用户在权限允许时看到同一研究上下文。
